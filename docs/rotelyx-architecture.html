What runs today

Every claim below is backed by a test that fails if the claim stops holding. The interesting part is not the count. It is that the unit tests all passed while three real privacy defects sat underneath them, and only cross-layer tests and tests over real sockets found those.

Three clients run the same stack. A command line chat, a native desktop window, and a local browser harness. They do not offer identical guarantees: the desktop client keeps plaintext inside one process, while the harness carries it across loopback. That difference is stated in the harness itself rather than smoothed over.

Found by testing

MLS was not padding at all

Overhead is a constant 145 bytes and the rest is one to one, so plaintext length leaked exactly. Worst on the direct peer-to-peer path, where there is no envelope to hide behind and this was the only length defence.

Found by testing

Padding buckets were too small

A 256-byte bucket held barely a hundred characters after MLS overhead, so ordinary messages straddled the boundary and told the operator “short” or “long” every time.

Found by testing

Dropped streams discarded data

A QUIC send stream dropped without finishing resets and silently discards data the sender believes was delivered. Write then drop is the obvious pattern; it lost the last message with no error anywhere.

The short answer

iroh is the right foundation. The homemade ratchet is not.

Own it

Derive the transport, own the policy

QUIC + TLS 1.3 with stateless relays replaces the whole ICE / STUN / TURN / DTLS / SCTP stack, and identity becomes an Ed25519 key rather than a phone number. Rotelyx ships that as rotelyx-net: our relay policy, our path selection, our discovery — on machinery derived from iroh, which is itself derived from Tailscale and quinn. Nobody in this lineage wrote NAT traversal from zero.

Reject

A custom Double Ratchet

A ratchet you write will be weaker than one you adopt — not because your algorithm is worse, but because the bugs live in state handling, not in the math. Use OpenMLS. Spend the saved months on the layer nobody has finished yet.

Reframe

"Impossible to access"

No system is. Claiming it costs you every serious reviewer in the first five minutes. Ship a written threat model that says what Rotelyx defends against and what it does not — that is what earns trust.

Foundation

What iroh hands you, and what it leaves entirely to you

iroh reached 1.0 on 15 June 2026 and is at 1.0.3. It is a Rust library with bindings for Swift, Kotlin, C, C++, Python and JavaScript — which matters, because your clients are phones. Multipath landed in February 2026; NAT-traversal hardening ran through March and April.

Solved for you
  • NAT traversal on any network. Direct hole-punched paths first, relay fallback when the path is impossible.
  • Stateless relays. Unlike TURN, an iroh relay forwards ciphertext without holding session state. Cheap to run, and it cannot read the stream.
  • Dial by public key. Identity is location-independent — the same node ID across Wi-Fi, cellular and home.
  • Authenticated transport encryption. QUIC + TLS 1.3, terminated at the two endpoints.
  • Datagrams and multiplexed streams in one connection — the media path and the chat path share a socket.
Still your problem
  • Asynchronous delivery. QUIC needs both peers live. Phones are not live. Nothing in iroh stores a message for an offline recipient.
  • Message-level crypto. No ratcheting, no post-compromise security, no group keys, no multi-device.
  • Metadata. A relay sees which node ID talks to which node ID. That is the social graph, in the clear, at the one place you were trying to make blind.
  • Prekeys and rendezvous. Something must publish "here is how to reach and encrypt to this identity" before the first connection exists.
  • The media stack. Transport ≠ jitter buffer, echo cancellation, congestion control. See below — this is the real cost.

iroh gives you a private pipe. It does not give you a private system.

Architecture

Five layers, two of which you actually build

Defence in depth means the transport encryption and the message encryption are independent. If TLS 1.3 in QUIC were broken tomorrow, L2 would still hold. If a device leaked an MLS epoch key, L1 and L0 would still deny an eavesdropper the raw stream. Never let one layer's key material derive from another's.

What "own" honestly means at L0 and L1. The derived machinery under rotelyx-net measures 122,786 lines — and half of that is a QUIC state machine (a fork of quinn) that upstream did not write either, while the hole-punching core is BSD-3 code derived from Tailscale. Rotelyx owns the parts where privacy is actually decided: relay policy, path selection, and discovery. Discovery is deleted rather than configured off, because upstream's default publishes your public key to a third-party DNS zone on every startup. The defensible claim is "our own transport, derived and substantially rewritten for metadata resistance" — not "written from scratch", which would be false and checkable.

L2 · the decision that matters most

Why MLS, and where you can genuinely go beyond the state of the art

The Double Ratchet is a two-party protocol. Every messenger that stretched it to groups did so with sender keys, which rekey in O(n²) and degrade post-compromise security exactly when a group is large enough to matter. MLS was built for this and 2026 is the year it stopped being theoretical: Discord ships it for end-to-end encrypted voice and video, and Google and Apple began rolling MLS over RCS in May.

What you adopt unchanged

openmls for the group state machine, the tree, the epochs and the ratcheting. It is the most-reviewed Rust MLS implementation and it is doing the part that is hardest to get right: state.

What you actually invent

A hybrid post-quantum combiner over MLS. RFC 9420's ciphersuites are all classical, and PQ suites are still in draft. Building X25519 + ML-KEM-768 hybrid key agreement in from day one is a real contribution — and the correct place to spend an audit budget.

What you deliberately skip

Writing a ratchet. Signal's own team needed PQXDH and then SPQR over several years, with formal analysis, to get post-quantum ratcheting right. That is the benchmark a homemade ratchet is competing against.

Custom crypto is not how you beat Signal. Metadata is.

The failures in a hand-rolled ratchet are almost never algebraic. They are nonce reuse under concurrency, state rollback after a crash or a restored backup, unbounded skipped-message key storage turned into a memory-exhaustion attack, replay across device re-registration, and non-constant-time comparisons. Every one of those is an implementation bug that a specification cannot save you from, and every one of them has shipped in a real product.

Topology · unresolved

"One private server" and "the phone hosts everything" cannot both be true

You described two different systems. They pull in opposite directions and the choice changes the threat model, the mobile engineering, and whether the product is usable at all. Here is the honest trade.

Topology Offline messages Metadata exposure Mobile viability Verdict
Pure P2P
phone hosts, Kik-style		 None — both peers must be online Relay sees node-ID pairs only iOS kills background sockets. Dead on arrival. Not shippable alone
Single central server Reliable One host sees the entire social graph Straightforward Recreates what you are escaping
Blind mailbox + P2P
recommended		 Opaque envelopes, short TTL, deleted on delivery Rotating tags, sealed sender, padded sizes Silent push wakes the P2P session Ship this

The recommended shape: when both peers are online, everything — messages, media, calls — flows direct over iroh and touches no server you operate. When the recipient is offline, the sender drops a fixed-size sealed envelope addressed to a rotating pseudonymous tag into a mailbox node that never learns the sender, never learns the plaintext, and deletes on delivery or TTL. The mailbox is self-hostable, so any user or community can run their own — that is the Kik-style autonomy you want, made survivable on real phones.

Push notifications are the leak nobody designs around. Apple and Google see that some message arrived for a device. Mitigate with content-free silent wakes, jittered delivery, and decoy pushes — and then write down in the threat model that you did not solve it, because you did not.

Media

Dropping WebRTC is correct and more expensive than it looks

The transport argument is settled. iroh-roq carries RTP over QUIC, and n0's own callme already does Opus audio over it with cpal for device access — Linux, macOS, Windows and Android working, iOS untested. It is explicitly experimental, which is the accurate description of where this path stands.

What you gain
  • No SDP, no ICE agent, no TURN bill, no DTLS handshake on top of a handshake.
  • Relays that cannot read media and cost a fraction of TURN.
  • One connection carrying chat, control and media with independent stream priorities.
  • Media keys derived from MLS, so a call is as end-to-end as a message.
What you give up
  • Fifteen years of libwebrtc tuning. Jitter buffer, packet-loss concealment, NetEq, acoustic echo cancellation, bandwidth estimation and congestion control are not transport features. You will port or rebuild all of them.
  • Browsers. WebRTC is still the only peer-to-peer media transport a browser will give you. A web client means a separate path.
  • Group calls above ~6. Full mesh stops scaling and an SFU breaks E2EE unless you add SFrame-style per-frame encryption keyed from L2.

Plan accordingly: audio-only 1:1 is reachable in weeks on top of callme. Audio that sounds as good as WhatsApp on a bad cellular link is the single longest task in this project — longer than the cryptography.

Benchmark

Telegram is the wrong target. Signal is the real one.

Beating Telegram is not an achievement worth designing toward — its default chats are readable by its servers and its group chats have no end-to-end encryption at all. Measure against Signal, where the honest reading is: you match on crypto by reusing the same primitives, and you win on the things Signal chose not to fight.

That last row is the whole difference between a strong design and a trustworthy product, and no amount of architecture closes it.

Distribution

Open source it, and say less while doing it

Yes — open source, permissively, from the first commit. A closed security protocol is not evaluable, and an unevaluable protocol has no security claim to make. Kerckhoffs's principle is not a philosophical preference here; it is the only mechanism by which anyone can believe you.

What to publish: the protocol specification as a document separate from the code, the Rust core, the threat model, and the test vectors. What to withhold: nothing technical. What to never write in the README: "unbreakable", "impossible to intercept", "military-grade". Those three phrases are how security researchers decide within thirty seconds that a project is not serious, and they are also simply false — every one of them will be disproved by a determined enough adversary against a device endpoint rather than against your cryptography.

Publish the threat model as a peer of the code. State plainly: Rotelyx defends against network adversaries, relay operators, mailbox operators and server seizure. It does not defend against a compromised endpoint, a malicious OS, coercion of a participant, or traffic-analysis by a global passive adversary. Naming those honestly makes the claims you do make credible.

Sequence

What to build, in this order

  1. Threat model document. Before code. It is what every later decision is checked against.
  2. Rust core crate. iroh endpoint, identity keys, node discovery, connection lifecycle. Prove two devices on different networks connect through a NAT.
  3. MLS integration. OpenMLS group state, 1:1 as a group of two, key packages published through the mailbox. Text messages only.
  4. Blind mailbox node. Sealed sender, padding buckets, rotating tags, TTL deletion. Self-hostable single binary.
  5. Hybrid PQ combiner. X25519 + ML-KEM-768 over the MLS key schedule, with test vectors published for review.
  6. Audio calls. Fork or depend on callme, key the media from MLS exporters.
  7. Mobile clients. UniFFI bindings, background lifecycle, silent push. The point where the project becomes real, and the point where most of the pain arrives.

Open decisions blocking step 1. Topology confirmation — is the blind mailbox acceptable, or is pure P2P a hard requirement you are willing to pay for in usability? Platform priority — desktop first, or mobile from the start? And whether the post-quantum combiner is in scope for v1 or deferred, because it changes the audit scope and the timeline substantially.
